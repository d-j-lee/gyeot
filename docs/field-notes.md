## 2026-11-26 · 개발 컨테이너(Linux x86_64, Claude Code 2.1.332)

- **끝-끝(가짜 없음)**: `tests/e2e/e2e.mjs`로 실제 `gyeotd`·`gyeot-hook`·`gyeot-channel.mjs`(MCP SDK 클라이언트가 Claude Code 역할)·얼굴(Chrome 헤드리스)을 이었다. 39/39 통과.
  - 공식 문서의 페이로드 꼴로 만든 Claude Code 훅 입력으로 승인 대기 → `approval`(95) → 같은 세션에 방금 입력이 있으면 `ambient`, 다른 세션이면 `nudge`. 같은 도구의 `PostToolUse`로 닫힘.
  - 질문으로 끝난 `Stop` → `decision`. `/v1/say` → `notifications/claude/channel` 도착(meta 키 식별자, `from=dj`·`via=gyeot`). `reply` → 얼굴 SSE `reply`. `request_decision` → 선택지 카드 → 선택이 `[선택]` 메시지로 같은 세션에 돌아옴.
  - 하네스 `gate` `block` → `failed`, 존재감 `alert`. 데몬 재시작 뒤 항목이 재생으로 같음. 프롬프트 본문은 로그에 없음. 데몬이 꺼져 있을 때 훅은 5ms 안에 exit 0, stdout 비어 있음, 스풀에 남고 데몬이 다시 뜨면 비워짐.
  - pid 연결: 이 시험에서는 훅과 channel의 부모가 같은 프로세스라 `pid_hint == ppid`로 이어졌다. **실제 Claude Code에서 이렇게 되는지는 F1로 남는다.**
- **실제 Claude Code 훅 실행 시도(실패, 환경 탓)**: 이 컨테이너 안에서 `claude -p --settings …`로 곁 훅을 건 중첩 세션을 띄웠다. 인증 오류("Authentication error")로 턴이 끝났고, 셸 형식 기록 훅을 같이 걸어도 아무 훅도 실행되지 않았다. 이 컨테이너는 관리되는 하위 세션 환경(`CLAUDE_CODE_CHILD_SESSION`, policy-limits)이라 중첩 세션의 훅·인증이 막힌 것으로 본다[추론]. **실제 훅 페이로드 대조는 사용자 Windows에서 F1과 함께 한다.** 정규화는 공식 hooks 레퍼런스(2026-11-26 열람)의 필드 이름을 따랐다.

## 2026-11-26 · GitHub Actions windows-latest(실행 45695614602, 커밋 8f464bc, R1 수정본)

- 실패 2건, 나머지(rust·e2e ubuntu, face, channel, shell windows, scripts 5.1·7) 통과.
- **`POST /v1/boot`가 Windows에서 응답을 잃었다**: 서버 시험 2개가 상태 0(빈 응답)으로 실패. 서버가 본문(`{}`)을 읽지 않고 답한 뒤 연결을 닫으면, 늦게 온 본문 때문에 Windows가 RST를 보내 클라이언트가 이미 받은 응답까지 잃은 것으로 본다[추론]. Linux에서 "머리만 보내고 150ms 쉬기"로 서버가 본문 전에 답하는 것을 재현했고[확인], 처리기가 본문을 끝까지 읽게 고쳤다. 셸의 "곁 열기"와 `gyeotd --open`이 같은 요청을 보내므로 실제 사용에도 걸리는 문제였다.
- **Windows 끝-끝에서 Chrome 원격 디버깅에 15초 안에 붙지 못했다**: v0.1 실행에서는 붙었다. 원인은 로그가 없어 모른다[미확인]. 빈 포트를 미리 잡았다 놓는 방식을 버리고 Chrome이 고른 포트(`DevToolsActivePort`)를 읽게 바꿨고, 기다림을 45초로 늘렸고, Chrome stderr를 산출물에 남긴다.
- 데몬이 꺼져 있을 때 훅: **161ms**(v0.1의 같은 줄 430ms). connect 단계 한도 100ms의 효과로 본다. 표본은 실행마다 하나다.

## 2026-11-26 · 회귀 검증 R2와 새 눈 검증 R3(개발 컨테이너, 커밋 8f464bc)

두 에이전트가 각자 사본에서 동시에 돌았다. R2는 R1 발견 목록을 받아 전후 판을 같은 실험으로 대조했고(약 23분), R3은 목록 없이 최신 변경을 공격했다(약 20분).

**R2 판정**: FIXED 9(H1·M1 원래 경로·M2·M3·M4·L1·L2·L3·L4·L6), PARTIAL 3(H2·M1·L5).
- H1: 실제 Chrome으로 `?api=`를 다른 포트로 준 얼굴을 열었다. 수정 전 리스너가 Bearer 3회·`?t=` 3회를 받았고, 수정 뒤 0회.
- M3: 비밀이 든 페이로드 9종. 수정 전 스풀에 원문·0644, 수정 뒤 0회·0600·폴더 0700. 줄이기 동등성 퍼즈 30,000건에서 `normalize(원본) != normalize(줄인 것)` 0건.
- PARTIAL의 이유는 새 문제로 이어진다: N1(`--open`이 코드를 프로그램 인자에 실어 다른 Linux 사용자가 `/proc`로 읽고 먼저 세션을 받음, 실측), N2(승인한 도구가 2분 넘게 돌면 여전히 소리 알림, 실측), N3(병합 감지가 `+main`·`refs/heads/main` 등 8가지를 놓침).
- 공허한 시험 1건: `redirect_location`의 점 조각 검사를 지워도 시험이 통과했다(다른 검사가 같은 사례를 잡음).

**R3 발견**: 높음 1·중간 4·낮음 6.
- 높음 H1: 세션 쿠키가 `127.0.0.1`의 다른 포트로 샜다. 다른 사이트가 그 포트로 넘기기만 해도 그 페이지의 하위 요청(img·fetch·favicon)에 쿠키가 실렸고(Chrome 헤드리스 실측), 그 쿠키로 `/v1/say`가 진짜 channel에 "사용자가 허락했어요"라는 글을 넣었다. G-028에 "받아들인 위험"으로 적었던 전제(다른 사이트에서 건너오면 안 붙는다)와 완화책(`*.localhost` 전용 이름)이 둘 다 틀렸다.
- 중간: M1 쿠키로 ingest·channel까지 열림(channel 가로채기 실측), M2 포트를 먼저 잡은 다른 사용자에게 토큰이 감(심·`--open` 실측), M3 다른 하위 에이전트의 `PostToolBatch`가 진짜 승인 대기를 닫음(코어 실측), M4 `%LOCALAPPDATA%` 밖 설치 폴더의 Windows 권한(추론).
- 낮음: 거절 뒤 승인 대기 남음, 늦게 온 옛 신호, 일반 `키=값` 비밀 마스킹 누락(실측), Unix 데이터 폴더 0755·파일 0644(실측), 결정 카드를 권한 승인처럼 꾸밀 수 있음(실측), Windows 대소문자 경로(추론, 비밀 없음).

이 결과로 계약 §12.1을 다시 쓰고 §13을 더했다(G-030~G-035). 고친 판의 검증은 아래에 잇는다.
